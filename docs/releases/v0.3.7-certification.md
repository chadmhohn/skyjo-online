# Flipvale external-beta policy v0.3.7 release certification

> Preparation status: this document and matching version metadata prepare a candidate only. They are not evidence that `v0.3.7` exists, that production has moved, or that issue #191 is complete.

`CERT_SHA` is the exact protected-main commit selected after the public policy source and release-preparation patch merge.

## Required production precondition

Before tagging, confirm v0.3.6 is healthy production `current`, production `previous` is an exact immutable release, and `/healthz`, `/readyz`, `/version`, AASA, account, room, invite, Web Push, and APNs checks are healthy. v0.3.3 is the permanent minimum code-rollback target. The v0.3.7 candidate must not alter public schema 2, room persistence 2, multiplayer protocol 2, contract bundle 1, solo-AI strategy 1, or the frozen APNs descriptor.

- Publishes unauthenticated `/privacy` and `/support` routes for Flipvale, grounded in the repository-owned data inventory and account-deletion retention contract.

## Exact-SHA certification gates

1. Review `v0.3.6..CERT_SHA`; confirm package, both root lockfile fields, changelog, certification constants, CI, and nightly evidence identify `0.3.7`.
2. Require release/account/invite/chat/APNs/delivery smokes; unit, contract, browser, accessibility, runtime-artifact, load/recovery, and networking-contract checks. Native jobs may use the documented no-native-change placeholders for this server-only release.
3. Require every protected-main check and exact-SHA CodeQL result to pass. CodeQL does not run automatically on tag pushes, so retain the protected-main result for the same SHA.
4. Require an independent second-agent review of the exact final SHA, including public-route access, policy accuracy against the repository inventory, bundle isolation, compatibility, and rollback behavior.
5. Confirm without printing values that the existing APNs provider configuration remains complete. `GET /api/push/apns/config` must continue to return exactly `{"enabled":true}` for an authenticated account.
6. Obtain explicit approval in the current conversation naming both exact annotated tag `v0.3.7` and exact `CERT_SHA`. General autonomy is insufficient for this production tag and deployment boundary.
7. Require tag CI to prove the annotated ref, version metadata, tested checkout, deterministic runtime subjects, provenance, isolated credentialless canary, copied-state compatibility, pre-activation backup, and production promotion.

## Post-promotion release closure

After production is healthy at `CERT_SHA`, start from a clean checkout of the immutable tag and download the successful tag-run inputs:

```sh
gh run download "$TAG_RUN_ID" \
  --repo chadmhohn/skyjo-online \
  --name "skyjo-build-$CERT_SHA" \
  --dir .
gh run download "$TAG_RUN_ID" \
  --repo chadmhohn/skyjo-online \
  --name "certification-$CERT_SHA-$TAG_RUN_ID-$TAG_RUN_ATTEMPT" \
  --dir test-results
npm run certify:verify -- \
  --release-sha "$CERT_SHA" \
  --tag v0.3.7 \
  --production-base-url https://skyjo.groundworkrevops.com
```

Only after that verifier passes may an operator publish the GitHub Release from the existing tag. Attach the required exact-run evidence, runtime archive, checksum, SBOM, and every SHA-256 sidecar. Read the published release back through GitHub and verify its tag, source SHA, assets, checksums, and provenance.

Before promotion, revert the squash commit. After promotion, use only the immutable controller's code rollback to exact immutable v0.3.6 or another healthy release no older than v0.3.3. Never move a tag, manually relink releases, restore live data automatically, or remove the frozen APNs table.
