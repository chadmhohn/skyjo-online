# v0.2.0 independent agent persona handoff

Run these three reviews concurrently after the issue #72 squash merge and protected-main certification. Each agent receives a detached read-only worktree at the same `CERT_SHA`, an isolated local exact-SHA server/state set, and only its persona below. Use fresh isolated browser state and disposable accounts. Do not let agents read one another's report until all three are final. The disposable external HTTPS candidate is staged only after all three agents pass.

The automated eight-client Playwright gate is prerequisite evidence, not a substitute for these independent usability reviews. A code author cannot approve their own SHA.

## Persona A: first-time phone guest

Use a fresh mobile browser profile with no Skyjo storage. Follow a long group invite through the install/browser decision, fresh one-time install code, account creation, room join, offline installed cold launch, safe update handoff, touch-only two-player opening/turn, background/network recovery, and stale-invite messaging. Check that an update never reloads an active game and that APIs, invite pages, cookies, room data, and user data are absent from caches.

## Persona B: accessibility and constrained mobile

Use 320x568 at 200% text, keyboard-only desktop, reduced motion, and automated Axe. Complete opening reveals and a full turn; inspect semantic grids/cells, announcements, 44x44 targets, modal focus trap/restore, horizontal containment, contrast, guidance visibility, and hidden-state redaction in DOM/storage/cache/console. VoiceOver remains physical step I4 and must not be claimed here.

## Persona C: eight-player host and recovery

Use eight isolated authenticated clients. Verify connected-only start, all 16 opening reveals, command/revision convergence, per-player hidden-state redaction, 60-second waiting host transfer, 120-second active-seat grace/AI takeover, later same-seat human reclaim after the atomic AI action, chat/state propagation p95, half-open recovery, and unchanged-seat restart resynchronization. Check the centered table and large-roster scroll/animation behavior at phone, tablet, and desktop sizes.

Run the canonical eight-client certification before independent lifecycle exploration. Its propagation timing uses Playwright WebSocket routing/callbacks and one Node monotonic clock from forwarding the matching outbound command to the server through the last browser's incoming snapshot callback, with constant-time per-client arrival markers for exactly 18 state operations and 20 unique chat messages. The complete frame history is copied only once afterward for privacy inspection. Do not replace this with a poller that clones cumulative frame arrays, and do not invent a parallel authentication harness; use the repository fixture's disposable access session and accounts. Both browser propagation p95 values must remain at or below 250 ms with one worker and zero retries.

## Sanitized report contract

Each agent returns exactly this shape in its final message. Do not include emails, credentials, cookies, invite tokens/codes, room/player IDs, absolute paths, SQL, logs, or raw frames.

```yaml
persona: A | B | C
sourceSha: 40 lowercase hex characters
candidateIdentity: pass | fail # local /version and /readyz match sourceSha, schema 2, protocol 2
result: pass | fail
scenariosPassed: integer
scenariosFailed: integer
blockingFindings:
  - severity: P0 | P1
    area: short product area
    symptom: short sanitized description
nonBlockingNotes:
  - short sanitized note
```

The report is invalid if its SHA differs, a measurement is missing/non-finite, a scenario was skipped, or candidate identity failed. Any P0/P1 finding blocks the release. The orchestrator assigns the defect to its owning issue, repairs it, and reruns all automation and all three personas from the new protected-main SHA. Reports from different SHAs cannot be combined.
