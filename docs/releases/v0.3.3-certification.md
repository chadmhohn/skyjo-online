# Skyjo native-backend and rollback-envelope v0.3.3 release certification

> Preparation status: this document and its matching version metadata prepare a candidate only. They are not evidence that `v0.3.3` exists, that production has moved beyond the dated `v0.3.2` observation, or that issue #203's two-release production gate is complete.

`CERT_SHA` means the exact protected-main commit selected after this patch merges. It must contain frozen APNs-envelope source commit `f842937e7515e4f5d854644e5f7929bde5da5312`; the release verifier enforces that ancestry. Re-read public `/version` and `/readyz` before promotion rather than treating repository metadata as deployment state.

## Candidate scope since v0.3.2

This is a runtime-bearing release and is not byte-equivalent to `v0.3.2`. Prior automated, persona, or physical-session evidence cannot certify the changed server on its own.

- Contract bundle v1 adds language-neutral schemas and deterministic fixtures for operational identity, account/access/stats/invite HTTP, game state, public room snapshots, and both directions of protocol v2. The bundle version remains independent of server release, public database schema, and multiplayer protocol versions.
- The server adds strict JSON access-session endpoints and stable, sanitized API-error codes for native account, stats, room, and invite consumers. Browser form login, the shared site gate, account authentication, and room-membership rules remain in force.
- Protocol v2 remains version 2 while its parser, snapshot checks, command validation, UTF-16 bounds, and mixed native/PWA evidence are hardened. The immutable cached-PWA v0.3.2 validator pin remains a compatibility gate; it is not changed to the candidate release.
- `/.well-known/apple-app-site-association` becomes a direct public, bounded-cache invite-only association. Production startup requires the confirmed complete Apple application identifier; the fixed synthetic identifier is restricted to tests and isolated canaries. `?open=browser` remains the explicit browser fallback.
- `POST /api/rooms/invite/redeem` accepts only a bounded signed invite token before the shared access gate, applies a separate rate limit, returns only room code and expiry, and grants only the outer access session. It does not sign the user into an account or bypass room membership.
- The schema-2 account store freezes and validates optional APNs device-storage envelope version 1. This release accepts an absent table or the exact future table and preserves representative encrypted rows through copied-state backup, concurrent startup, readiness, and shutdown; it never creates, queries for product behavior, mutates, or deletes the table.
- The committed unsigned native target now includes the source-only v0.1.0 solo launcher and game table: explicit replacement, 1-7-bot fixed/Mixed setup, account-partitioned saves and stats recovery, board-first phone/iPad layouts, accessible summaries/settings, and provenance-checked audio. Its four-role UI/accessibility gate and exact archive-resource audit are repository release gates, but the VPS artifact does not distribute a signed iOS app. Apple credentials, device tokens, signing assets, and APNs keys are outside this release.
- Shared Swift and TypeScript opening guidance now uses viewer-neutral `Name: reveal 2 cards.` wording, with matching deterministic fixtures. This text-only runtime behavior does not change contract bundle 1, multiplayer protocol 2, shared snapshot envelope 2, solo-AI strategy 1, database schema 2, or room-persistence version 2.

Production dependencies, public database schema 2, room-persistence version 2, and multiplayer protocol 2 remain unchanged. Development-only contract validators are part of the repository toolchain. The changed server, invite, persistence-validation, and public-association behavior means no v0.3.2 byte-equivalence claim is permitted.

## Post-promotion release closure

After production is healthy at `CERT_SHA`, download the exact tag-run AI and certification artifacts rather than regenerating them, and stage them under the verifier's default `test-results/ai` and `test-results/certification` paths. From a clean checkout of the immutable tag, run the verifier with the production binding:

```sh
npm run certify:verify -- \
  --release-sha "$CERT_SHA" \
  --tag v0.3.3 \
  --production-base-url https://skyjo.groundworkrevops.com
```

Only after that command passes may an operator publish the GitHub Release from the existing immutable tag. Attach the exact tag-run `automated.json`, `eight-client-personas.json`, `recovery-trials.json`, `rss-stages.json`, and `benchmark.json` evidence with every SHA-256 sidecar, plus the runtime archive, archive checksum, and CycloneDX SBOM. Read the published release back through GitHub and require tag `v0.3.3`, non-draft, non-prerelease state, and the exact expected asset-name set. Download those assets into a fresh directory, re-run every checksum verification, verify the runtime attestation against `CERT_SHA` and `refs/tags/v0.3.3`, and record the release URL and asset inventory in sanitized issue evidence. A successful production promotion without the post-promotion verifier, published-release readback, evidence attachments, and downloaded checksum/attestation proof is not release closure.

## Two-release rollback-anchor acceptance

Promotion of `v0.3.3` is only release one. After it is healthy `current`, keep issue #203 open and #204 blocked. Do not create or use `apns_devices` yet.

Prepare a later healthy successor release that contains the same envelope but not #204's table creation/use. That successor needs its own coherent version metadata, exact-SHA full certification, and a second explicit approval in the current conversation naming its exact tag and SHA. After promoting it, prove all of the following before closing #203 or unblocking #204:

- `current` resolves to the healthy successor's exact attested artifact and public identity;
- `previous` resolves to the exact immutable `v0.3.3` tag, `CERT_SHA`, and attested artifact recorded after release one;
- the `v0.3.3` previous release starts against a copied schema-2 database containing the exact frozen APNs table, remains ready, and preserves every representative encrypted row byte-for-byte;
- both promotion records, backups, readiness results, public smokes, symlink resolutions, and explicit approvals are retained as sanitized issue evidence.

Only that exact verified-`previous` state completes #203. Once #204 later creates the table, `v0.3.3` is the permanent minimum code-rollback floor: never select a pre-envelope release, relink an older artifact, or restore a pre-table database to make an older rollback appear viable.
