# Skyjo open-access v0.3.6 release certification

> Preparation status: this document and matching version metadata prepare a candidate only. They are not evidence that `v0.3.6` exists, that production has moved, or that issue #228 is complete.

`CERT_SHA` is the exact protected-main commit selected after the open-access source PR and this release-preparation patch merge.

## Required production precondition

Before tagging, confirm v0.3.5 is healthy production `current`, production `previous` is an exact immutable release, and `/healthz`, `/readyz`, `/version`, AASA, account, room, invite, Web Push, and APNs checks are healthy. v0.3.3 is the permanent minimum code-rollback target. The v0.3.6 candidate must not alter public schema 2, room persistence 2, multiplayer protocol 2, contract bundle 1, solo-AI strategy 1, or the frozen APNs descriptor.

## Candidate scope since v0.3.5

- Removes the active shared site-password gate from browser, HTTP API, WebSocket, and native bootstrap paths. Guest solo and ordinary account signup/sign-in open directly; multiplayer, stats, profile, push, and account state remain account-authenticated.
- Keeps the compatibility access-session endpoints bounded and password-free for already-installed clients. Logout still clears both account and legacy access cookies, and rollback configuration may retain the old secret without active behavior depending on it.
- Preserves reusable invite URLs and five-character room codes without granting account identity, room membership, or automatic admission. Cached PWA and legacy native upgrade behavior remains deterministic.
- Requires JSON for signup/login, applies bounded signup and login rate limits using the validated trusted-client address behind the documented loopback Cloudflare Tunnel, and exposes stable rate-limit errors to web and native clients.
- Keeps production dependencies, the public migration ledger and readiness schema at version 2, APNs storage/encryption/provider behavior, and immutable deployment mechanics unchanged.

## Exact-SHA certification gates

1. Review `v0.3.5..CERT_SHA`; confirm package, both root lockfile fields, changelog, certification constants, CI, and nightly evidence identify `0.3.6`.
2. Require release/account/invite/chat/APNs/delivery smokes; unit, contract, browser, accessibility, runtime-artifact, load/recovery, and networking-contract checks; mixed native/PWA room flows; and the four-role UI/accessibility matrix.
3. Require every protected-main check and exact-SHA CodeQL result to pass. CodeQL does not run automatically on tag pushes, so retain the protected-main result for the same SHA.
4. Require an independent second-agent review of the exact final SHA, including open access, remaining account authorization, JSON media enforcement, proxy trust, rate limiting, invite isolation, compatibility clients, native bootstrap, and rollback behavior.
5. Confirm without printing values that the existing APNs provider configuration remains complete. `GET /api/push/apns/config` must continue to return exactly `{"enabled":true}` for an authenticated account.
6. Obtain explicit approval in the current conversation naming both exact annotated tag `v0.3.6` and exact `CERT_SHA`. General autonomy is insufficient for this production tag and deployment boundary.
7. Require tag CI to prove the annotated ref, version metadata, tested checkout, deterministic runtime subjects, provenance, isolated credentialless canary, copied-state compatibility, pre-activation backup, and production promotion.

## Post-promotion release closure

After production is healthy at `CERT_SHA`, start from a clean checkout of the immutable tag and download the successful tag-run inputs:

```sh
gh run download "$TAG_RUN_ID" \
  --repo chadmhohn/skyjo-online \
  --name "skyjo-build-$CERT_SHA" \
  --dir .
gh run download "$TAG_RUN_ID" \
  --repo chadmhohn/skyjo-online \
  --name "certification-$CERT_SHA-$TAG_RUN_ID-$TAG_RUN_ATTEMPT" \
  --dir test-results
npm run certify:verify -- \
  --release-sha "$CERT_SHA" \
  --tag v0.3.6 \
  --production-base-url https://skyjo.groundworkrevops.com
```

Only after that verifier passes may an operator publish the GitHub Release from the existing tag. Attach the required exact-run evidence, runtime archive, checksum, SBOM, and every SHA-256 sidecar. Read the published release back through GitHub and verify its tag, source SHA, assets, checksums, and provenance.

## Production acceptance

- `/` and ordinary client routes open without an access cookie or password form; the legacy access-session read reports available without accepting or logging a password.
- Signup/login work from fresh browser and native sessions; invalid media types and bounded same-client abuse fail with the documented stable errors; account-required HTTP and WebSocket actions remain unauthorized for guests.
- Existing accounts, rooms, reusable invites, cached PWA clients, legacy native clients, Web Push, and APNs remain compatible. Native physical-device and TestFlight validation remains in #190 after this compatible backend promotion.
- Production `previous` is exact immutable v0.3.5, and the recorded code rollback floor remains no older than v0.3.3.

## Rollback

Before promotion, revert the squash commit. After promotion, use only the immutable controller's code rollback to exact immutable v0.3.5 or another healthy release no older than v0.3.3. Never move a tag, manually relink releases, restore live data automatically, or remove the frozen APNs table.
