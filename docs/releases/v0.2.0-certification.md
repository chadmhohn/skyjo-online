# Skyjo PWA Polish v0.2.0 release certification

This is the exact handoff from protected-main certification to the immutable `v0.2.0` production release. `CERT_SHA` always means the 40-character protected-main squash commit, never the pull-request head.

## Automated release gate

The issue #72 pull request must pass every required context, including `CI / Load & Recovery`, and an independent non-author review. After its squash merge, reopen issue #72 and freeze the resulting `CERT_SHA`. Any later commit invalidates all evidence below.

Require the protected-main run for `CERT_SHA` to pass quality/security, domain/data tests, Chromium/WebKit, visual/accessibility, Lighthouse, exact-topology load/recovery, runtime artifact, provenance attestation, and the isolated VPS canary. Download these exact sanitized assets from that run:

- `automated.json`
- `automated.json.sha256`
- `k6-summary.json`
- `recovery-trials.json`
- `recovery-trials.json.sha256`
- `rss-stages.json`
- `rss-stages.json.sha256`
- `eight-client-personas.json`
- `eight-client-personas.json.sha256`
- the runtime archive, archive SHA-256, CycloneDX SBOM, and GitHub provenance

Verify the combined evidence locally with:

```sh
npm run certify:verify -- \
  --release-sha "$CERT_SHA" \
  --evidence test-results/certification/automated.json \
  --checksum test-results/certification/automated.json.sha256 \
  --recovery-evidence test-results/certification/recovery-trials.json \
  --recovery-checksum test-results/certification/recovery-trials.json.sha256 \
  --rss-evidence test-results/certification/rss-stages.json \
  --rss-checksum test-results/certification/rss-stages.json.sha256
```

The evidence is accepted only for package version 0.2.0, schema/protocol 2, Node 24, pinned k6 v2.0.0, and the exact built source. Counts and thresholds fail closed; missing, non-finite, sanitized-away, or manually reordered evidence is invalid.

`eight-client-personas.json` uses the persona-specific format v2 contract and must contain the canonical browser propagation evidence: exactly 18 state samples (16 opening reveals, blind draw, and replacement) and 20 distinct chat samples observed by all eight clients. Arrival timing is callback-driven on one Node monotonic clock, validates protocol v2 on both directions plus unique valid command IDs, binds each probe to the expected sender, command revision, and exact action payload (including card index or chat marker), starts when that routed outbound WebSocket command is forwarded to the server, and ends at each browser's incoming frame callback. A bounded, identifier-digested command ledger rejects sends observed before a probe is armed, duplicate revisions, duplicate IDs, and replays; retained diagnostic frames are never cloned in the timing loop. The JSON and SHA-256 sidecar are written before threshold rejection so a sanitized failure distribution survives, while raw browser frames, traces, server logs, identifiers, and credentials are excluded from the certification artifact. State and chat p95 must each be at most 250 ms, and the full redacted-frame privacy audit remains a separate non-timed pass.

## Independent usability gate

Run the three isolated agent personas in [v0.2.0-persona-handoff.md](v0.2.0-persona-handoff.md) concurrently against local isolated builds and state at `CERT_SHA`. Agents must not see one another's report until all three are final. The author cannot be the final reviewer. Any defect returns to its owning implementation issue, and all automated and persona evidence is regenerated from the repaired protected-main SHA.

After the three agents pass, stage the exact attested runtime artifact on `127.0.0.1:4182` with a fresh database, room file, cookies, accounts, application secrets, and a disposable candidate-only coherent VAPID key pair. The VAPID subject is different: it must be a real public-DNS HTTPS or mailto contact URI controlled by the operator (for example, `https://skyjo.groundworkrevops.com`), never a special-use host such as `.test`, `.example`, `.invalid`, `.alt`, or `.arpa`, localhost, or any IP literal. Prove startup accepted the complete key pair and public subject before subscribing the device. Make production state and secret paths inaccessible to the candidate; never copy production environment or state files. The candidate `/version` and `/readyz` must report `CERT_SHA`, schema 2, and protocol 2.

Expose only that localhost port through a disposable Cloudflare Quick Tunnel. Launch cloudflared with `env -i`, an isolated `HOME`, and an explicit zero-byte `--config` file; also make `/etc/cloudflared` inaccessible because cloudflared v2026.3.0 may discover its system config even when `HOME` changes. Do not reuse or modify the production tunnel or service. Prove both external HTTPS and WSS against the exact candidate before the device session, then follow [v0.2.0-device-session.md](v0.2.0-device-session.md).

## Tag, production, and publication order

Only after the physical session passes:

1. Create `v0.2.0` exactly at `CERT_SHA` and push it once. Never retarget or recreate the tag.
2. Require the tag workflow to repeat every automated gate, provenance verification, backup, migration canary, and isolated VPS canary.
3. Allow `CI / Production` to promote the already-proven artifact atomically.
4. Require local readiness, exact release SHA, authenticated app/WebSocket smoke, then public Cloudflare health, login, manifest, version, and readiness checks.
5. If post-activation verification fails, require the controller's code-only rollback and verify the previous release. Never automatically restore a live database after traffic may have resumed.
6. Verify the deployed release and evidence together:

   ```sh
   npm run certify:verify -- \
     --release-sha "$CERT_SHA" \
     --tag v0.2.0 \
     --production-base-url https://skyjo.groundworkrevops.com \
     --evidence test-results/certification/automated.json \
     --checksum test-results/certification/automated.json.sha256 \
     --recovery-evidence test-results/certification/recovery-trials.json \
     --recovery-checksum test-results/certification/recovery-trials.json.sha256 \
     --rss-evidence test-results/certification/rss-stages.json \
     --rss-checksum test-results/certification/rss-stages.json.sha256
   ```

7. Only now publish the GitHub Release for existing tag `v0.2.0`. Attach `automated.json`, `recovery-trials.json`, `rss-stages.json`, `eight-client-personas.json`, all four SHA-256 sidecars, the runtime archive checksum, and SBOM. Do not build, tag, deploy, or publish from the release command.
8. Remove the isolated physical-test candidate, close issue #72 and the program epic, and close the milestone only after the published release and production identity are read back successfully.

Production failure creates or updates the single sanitized P0 incident. Stop only for unavailable credentials/access, a provider/VPS outage, or destructive data recovery that requires selecting a backup.
